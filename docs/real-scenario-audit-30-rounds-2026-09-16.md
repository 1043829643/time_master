## 结论与范围

完成 **30 轮连续真实 Qwen 对话请求**，26 轮返回 200，4 轮返回 422（第 1、3、7、10 轮）。请求耗时中位数约 15.1 秒，最长 60.4 秒。200 仅代表接口有回复，不能代表用户需求完成：本轮确实发现错误时间、被否定的条目仍保留、分析与建议被全量清单替代等问题。

以一个同时做宣传片、摄影课和商场快闪的用户为主线，穿插不完整回答、改口、插事、撤回、部分资料到齐、工程搬家、延期再看、长期习惯与单次例外、截止提前、做完返工和跨零点会议。第 3、22、30 轮根据前序实际结果调整了输入，原话以逐轮记录为准。

测试运行于本机隔离账户，调用应用实际 `/api/qwen/chat` 和真实 Qwen 服务。30 轮均为 API 对话，没有把浏览器点击、麦克风、线上登录或微信发送算作本轮通过项。每轮核对原话、回复、实际方案、保存状态和当前记忆；方案经检查后，使用应用同一保存接口模拟明确确认。所有聊天请求都没有自动写入业务记录，记忆则会自动写入。

**测试干预公开记录：**

- 第 1、3 轮新建项目均失败。第 3 轮后手工建立用户原话中的快闪项目、并行事项、联系人关联、工程和随手记，供后续场景继续使用。不能将这部分算作助手成功创建。

## 根因证据与长期修复要求

1. **保留收到的原话和失败状态。** `app/api/qwen/chat/route.ts` 通过完整校验后才 `commitChat`，因此失败轮次不进入下轮历史。应把输入接收、推理结果、提议、确认和失败作为可恢复的状态，重试保持幂等；失败原话可供理解，但必须明确未执行。
2. **用统一预览状态校验跨对象关系。** `lib/conversation-response.ts` 先调用 `applyOperations` 验证新对象，再用旧 `data` 校验记忆；`lib/conversation-memory.ts` 的subject集合只有已保存对象。需要以同一预览图核对新项目、任务、联系人和对应上下文。日志能证明引用错误，但未保留模型候选原文，无法断言第1/3轮具体哪个新ID触发。
3. **对每个意图验收，并显式处理否定。** 当前supersede会携带未覆盖的旧操作，第5轮被否定条目因此仍存在。每个子意图需要明确“已回答/待澄清/提议/撤回”，负向指令应排除相应条目；正文、方案摘要、实际操作应来自同一最终意图集合。
4. **记忆具有来源、确认程度和替代关系。** 已存事实、用户偏好、未决需求与助手推断应区别保存。不能因为附了原话quote就把推断当confirmed。改期仍是同一承诺的更新，不能因date变了就让两份记忆长期并行。应在取消/改期/应用时同步推进关联记忆生命周期。
5. **统一时间与容量约束。** 聊天和手动安排共用约束计算与预览，明确预计跨度、具体时段、截止时点、个人投入、他人工作和路程。未给时间的等待事项应支持待定，而不是为了满足必填dueAt静默生成日期。第9轮的硬结束时间必须在形成可确认方案前核验。
6. **按用户的问题组织回复。** `savedStatusSummary`可以提供确定性事实，但不能整段替换可行性分析、下一步推荐和文件查询。`describeChanges`应突出实际改变的字段；收尾只给当前最相关的事实、需要决定的事和下一步。继续在“今天 / 项目全景”原地处理，不增加主页面。
