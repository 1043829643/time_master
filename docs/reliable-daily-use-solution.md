# 时间管理大师：面向长期日常使用的修复方案

日期：2026-09-16。状态：设计方案，尚未实施。已补充Agent实际新增、修改和保存核对的要求。

依据：前一轮9轮真实场景及浏览器故障测试，以及[追加30轮真实Qwen测试](real-scenario-audit-30-rounds-2026-09-16.md)。目标是让多项目并行的用户放心记录、安排和推进，继续只保留“今天 / 项目全景”两个主入口。

## 1. 用户实际得到什么

| 用户行为 | 应有结果 |
|---|---|
| 想到哪说到哪，一次说项目、联系人、工程、时间 | 原话先可靠接收；已知内容被整理，只有真正影响执行的歧义才问一个问题。用户不需要按表单顺序说。 |
| “把摄影课小林的微信改成这个”“给快闪加一项验收” | 对象和内容明确、操作可逆且无冲突时，Agent直接执行并核对保存结果，回显实际变化和撤销入口。不能只回答一段建议或让用户再去表单录入。 |
| 助手没回复完，又补一句“不是周五，是下周四” | 两句话都保留，后一句更新前一句的相关决定。旧回复晚到也不能覆盖新决定。 |
| 只记个念头、还不知道哪天做 | 放入随手记，允许没有项目、日期、负责人；不擅自占日历。记录原文可以直接保存并提供撤销，模型推导出的安排仍需确认。 |
| “银行取消，小林别催，其他保留” | 清楚列出取消对象与保留对象；从最终方案中真正排除取消项。同一句的其他内容继续处理。 |
| “帮我分析一下，先别改” | 给出冲突、影响和可选办法，不提交业务修改，也不把助手建议写成已确认记忆。 |
| “只告诉我现在最值得做的一件事，15分钟以内” | 推荐一个有具体产出的下一步，说明为什么适合现在；不把整件两小时任务当作15分钟任务，不自动占日历。 |
| 收到部分材料、做了一部分、做完后又发现缺件 | 支持先推进可做的部分、记录剩余投入、重开原事项；保留原项目、任务及资料关联。 |
| 弱网、刷新、关面板、切入口、换设备 | 已收到的内容和未确认方案可恢复；未同步内容有清晰状态，重复点击不重复保存。 |

执行方式按用户本轮意图决定。用户明确要求执行、目标唯一、内容足够、操作可逆且通过校验时，指令本身就是本次操作的授权，Agent直接保存并给出精确回执与撤销入口，无需用户重复点击确认。涉及多少条记录并不单独决定是否需要再确认；有依赖的操作必须作为一组，避免“项目未创建、任务先保存”。

用户说“先看看、给建议、先别改”时仅预览；信息不明确、需要模型替用户作尚未决定的取舍或存在冲突时，在当前对话显示待决定项。用户已看过具体方案后说“就按这个”“可以，执行吧”，可确认唯一且仍有效的方案；若有多份候选，只问要执行哪一份，不能顺便应用其他方案。完整删除项目及其关联内容等影响较大的操作，先说明实际影响范围。所有确认都在当前入口完成。

这会调整当前应用“所有助手业务变更必须点击应用”的规则，属于待实施的新执行策略。现有测试里的未确认草案不会因升级被自动执行。

## 2. 两个入口内完成工作

### 今天

一个文字/语音入口，下面按实际需要展示下一步、今天时段、当前需要回应的等待事项。默认给出最相关的少量内容，可展开全部；不把未来所有催办和随手记同时堆上来。

对话结果就在原处显示：问文件给位置与复制按钮；问微信给联系人、项目角色与复制按钮；安排事情给时间和变更卡；更新进展给“还剩多少、下一步是什么”。待确认方案随对应对话展示，未完成处理有统一标记，无需来回切换“对话 / 方案 / 记忆”。历史方案和记忆管理放在详情中。

### 项目全景

每个项目平铺整个推进节奏，同一项目允许多条并行子事项。条块表示预计跨度，块内显示作用简称和状态；悬停、键盘聚焦或手机点按可看完整用途、负责人、阻塞原因、截止与下一步。

日历占用与项目跨度分别表达：阿南设计两天不等于占用我的两天；我的验收10分钟才进入个人日历。日期未定的事项留在该项目的待安排区域，不强行生成时间条。

点开项目或事项，在同一侧栏看相关联系人、微信、电脑、工程路径、跟进及进展。保留暖白、墨绿的视觉，颜色只表达少量明确状态；不用增加入口来承载内部处理状态。

## 3. 内部采用模块清晰的单体架构

继续使用现有应用和D1存储，复用已有操作回执、版本校验及基线合并。把职责从对话路由与解析器中拆清楚，不要求新增一套微服务运维。

处理顺序：**可靠接收输入 → 识别意图与对象 → 生成内部变更预览 → 校验内容、关系与执行范围 → 明确指令直接执行 / 未决部分在原处确认 → 原子保存 → 核对操作回执与实际结果 → 同步界面及关联状态。** 查询和仅分析在读取、核验事实后直接回答，不进入业务保存。

Qwen负责理解表达、提出解释和建议；对象存在性、日期时长、冲突、修改范围、版本和是否已经保存，由应用里的统一规则核对。模型结构异常时保留已接收原话、记录失败原因并提供重试，不把内部格式错误交给用户解决。

### 3.1 可靠接收与恢复

- 浏览器用按账户隔离的持久输入队列保存文字、编辑草稿和待处理录音；不能只有单个待传递字符串。先持久接收，再清空来源输入框。存储不可用时明确提示未保护，不显示“已保留”。
- 服务端在调用Qwen前保存请求原文、请求ID、内容指纹、前序关联和处理状态。状态区分已接收、处理中、需要澄清、已给方案、已完成、可重试失败、已取消；这些不是新页面。
- 同一请求ID和相同内容只产生一份结果；改了内容生成新请求并关联原请求。失败原话可以参与下一轮理解，但标明未执行，不能被当作业务事实。
- 取消等待和取消安排分开。停止等待不伪装成撤销已保存安排；后台迟到结果按当前请求版本处理。新改口可以使旧草案失效。
- 同一对话允许连续输入，处理时保持明确顺序；同一工作空间的并发写入用现有版本校验。不同记录可合并，同一字段冲突只展示差异，不要求用户刷新后重说整段话。
- 服务端请求持久化不等于浏览器关闭后一定继续运行。第一阶段保证重新打开能够续跑；若承诺离开页面仍继续整理，必须增加平台实际支持的持久任务执行与重试机制，并单独验收。

覆盖：F02、F12，以及上一轮连续输入覆盖、断网草稿丢失、保存时切页假失败。

### 3.2 每个意图有结果，部分改口有明确范围

- 为本轮每个独立需求建立意图项：原话范围、目标对象、读/分析/推荐/改/撤回、依赖、处理结果。一个问题不能因为同句话另有“收尾”就被吞掉。
- 实体解析同时查看已存记录、仍有效的草案和失败输入。不同小林用项目及角色消歧；仍无法确定才询问，其他明确问题正常回答。
- 新项目、新任务和联系人关联先进入同一临时预览，分配稳定ID，并按依赖关系验证。可以引用本次预览的新对象；此类上下文先归属于草案，应用后才晋升为已存事实，放弃后不会留下活跃孤立记忆。
- 每次方案修改显式表达保留、替换、移除哪些意图项。否定指令优先排除对应内容，禁止“旧条目未被覆盖就自动带回”。
- 已保存对象的取消生成相应变更；未应用方案的取消只更新草案状态。程序按对象状态选择动作，避免让模型自己拼出不合法的删除/保存混合操作。
- 相关变更作为原子事务保存，记录操作回执。独立意图可以分别处理，但必须明确哪些已完成、哪些等待决定，不允许一半失败却回复整件事已经安排好。
- 草案ID、执行请求ID与业务记录ID分开；从用户确认的具体方案和当前版本生成执行请求。实际执行继续走统一校验和保存服务，不能因“直接执行”绕过时间、引用或并发检查。

覆盖：F01、F04、F08及复合请求漏处理。

### 3.3 业务数据、偏好和草案上下文各有事实来源

- 日程时间、联系人微信、工程路径、跟进日期等已有结构化字段，以业务记录为事实来源。对话从这些记录读取，避免在自由文本记忆里再维护一份“当前日期”。
- 用户明确表达的长期偏好可随对话记住并提示；临时例外关联原偏好及具体日期/对象，不覆盖整个长期规则。
- 助手推断、建议、待确认安排保留在对应方案上下文中；不能因为quote真实存在，就把不同含义的statement记成confirmed。
- 记忆增加事实键、来源请求、关联记录/方案、有效范围、取代关系和生命周期。日期是事实值的一部分；同一承诺改期仍更新同一事实身份。
- 取消、改期和应用时，事务内同步关联事实的生效/失效状态；手工修改也走同一流程。历史保留用于解释与撤销，当前上下文只检索有效版本。
- 真正无法确定是否同一事实时，保留待确认冲突，不盲目覆盖，也不将两份矛盾值同时当已确认限制。

旧数据处理：先备份和审计，再识别与业务记录重复的日期记忆、已经取消方案的残留引用、同一来源链的旧版本。可证明过期的设为失效并保留历史；证据不足的标待核对，不让另一轮模型重新猜测后自动覆盖真实安排。

覆盖：F07、F09；长期使用时避免记忆越积越乱。

### 3.4 统一的安排校验与计算

以下概念分别存储：项目/任务预计跨度、明确截止及其精度、我的剩余投入、其他人的工作、实际日历时段、等待对象的承诺时间、下次主动跟进时间。明确“周五中午前”的截止不能只剩一个日期；只有日期时也不能伪装成用户给过精确时间。

- 跟进允许没有催办时间；“小林会给例图”可以先记录等待对象与内容。承诺交付时间和下次主动询问时间分开，用户未定的字段保留未定。
- 排程前核对固定安排、时长、硬开始/结束、路程、人员空闲、任务依赖、可用精力及长期偏好。跨零点按完整时间戳计算。
- “11:30结束、办30分钟、路上20分钟”算出11:00到、10:40出发；如果用户另外要求11:00出发，则解释矛盾并只问要保留哪个条件，不能偷偷延长结束时间。
- 只有截止前的可用预留可以抵扣截止前需要完成的投入。截止后的预约标为风险，不能抵扣成“今天不用做”；容量不足直接给缺口和可选调整。
- 一个项目允许并行子事项，只有真实依赖限制先后；他人的设计时间不计入我的日历容量。先粗剪室内和等待外景可分别推进。
- 所有排程入口使用同一计算与校验：对话、手动编辑、拖动、自动推荐均一致。硬冲突的草案先解释并给选择；若用户确实改变限制，重新生成满足新限制的方案，不通过静默改条件来“排成功”。

覆盖：F03、F06及上一轮固定冲突、截止失效、未来预留错误抵扣。

### 3.5 回答与执行收尾

- 查询返回所问对象；可行性分析返回结论、原因和选择；推荐返回一个下一步及依据；只有用户要求总览才展示总览。结构化事实提供依据，不再用全量状态表覆盖自然回答。
- 回复需要覆盖所有意图。方案卡和正文都使用最终变更集合，突出前后差异：例如“剩余投入改为80分钟”“不再催课程小林”“工程改到家里电脑E盘”。无法处理的意图清楚标出，不能悄悄消失。
- 收尾默认回答已落实、仍待确认、明日优先及一个待决定问题；用户同轮追问的路径/微信继续单独回答。没有待决定问题时明确说没有，不制造追问。
- 完成时段只代表结束一次投入；可快捷记录完成了什么、还剩多久、是否继续，不自动推断任务完成。用户直接报告任务已提交，则完成任务并检查尚未发生的相关工作时段。
- 区分用户主动暂停与外部资料阻塞。收到资料后解除对应阻塞，其他依赖仍存在就继续等待；主动暂停不能被自动恢复。旧waiting状态无法确认来源时，原地问一次“现在可以继续了吗”。
- 想法支持保留待整理、暂时搁置、指定日期再看、已转事项。搁置保留记录但退出日常待办压力；转换保留原文和目标关联。

覆盖：F05、F10、F11及上一轮等待恢复、投入收尾缺口。

### 3.6 语音进入同一条工作流程

录音使用已有本地保护能力并补齐中断恢复：录制完成后的音频先可靠保留，转写失败可重试或导出；浏览器终止前尚未持久化的片段不能声称已恢复。

转写文字与手打文字进入同一输入队列和操作流程。人名、时间和数字是关键字段：能取得可靠置信度时提示不确定部分；没有置信度时结合上下文矛盾检测和必要澄清，不能假装知道识别准确率。涉及安排的卡片必须看得见关键时间，用户可原地改字。

语音播放失败不影响文字回复和保存回执。支持停止播放、继续打字、刷新后恢复已保留录音；麦克风权限失败给明确的文字入口。取消录音不得进入发送队列，助手播放的声音不得被当作新的用户输入自动发送。站内跟进、系统日历提醒与外部微信发送分别说明实际能力，不暗示关闭网页后已经有推送，也不声称已代发微信。

### 3.7 Agent实际新增与修改的执行契约

目标是用户交代后，应用中的内容按要求发生变化。完成标准包含目标对象、字段内容、关联关系、保存结果和可见反馈，不能只检查工具是否返回200或回复是否流畅。

| 能力 | 执行要求 | 保存后核对 |
|---|---|---|
| 新建项目及子事项 | 一次请求中创建明确要求的项目、并行子事项和已知关联；缺少非必要资料允许待补。服务端分配稳定ID并检查相互引用 | 项目存在，子事项数量/内容符合要求、归属正确、并行事项没有被擅自串行依赖；不占用他人的个人日历 |
| 修改现有内容 | 按项目、上下文、角色查找稳定ID；在当前记录上执行明确字段补丁，保留未涉及字段 | 改的是原记录，其他名称/截止/负责人/关联没有被模型整条重写或重置 |
| 追加说明或进展 | 区分追加、替换、清空和更正；用户说“补一句”时保留旧内容和原文来源；字面指定的文字原样保存，润色仅在用户要求时进行 | 原文还在，新内容出现一次，追加位置正确；重试不重复追加，不能把本轮短句当整段替换 |
| 联系人和工程资料 | 新增/更新联系人项目职责、微信、电脑和路径时保持对应关系；同名但不同人不合并 | 原联系人ID及其他项目角色保留；工程更新属于正确项目，最新路径可在项目侧栏找到 |
| 改期、撤回、重新打开 | 已存记录更新原ID；旧草案撤回；需联动的时段、阻塞和记忆在同一操作组处理 | 原值不再作为当前安排生效；没有重复记录，被排除条目没有复活；未涉及内容保持原样 |
| 用户确认具体方案 | 解析“就按这版”指向当前唯一有效方案；应用前按最新状态再次校验 | 执行方案版本与用户确认版本相同；如果关键字段已被另一台设备修改，只处理该冲突，不能换个新方案自动执行 |

执行器需要窄而明确的业务工具：查询对象、创建对象、修改指定字段、追加内容、移动日程、取消事项/方案、更新进展、调整关联、查询操作结果。底层可以复用现有操作格式，但由统一执行器构造字段补丁和事务，模型不直接替换整份工作空间。

每个执行项记录原话依据、目标ID、前置版本、允许改动字段、依赖组和预期结果。必须核对“用户要求的变化出现了”和“禁止/无关的变化没有出现”；原话引用只帮助追溯，不能单独证明语义正确。关键字段使用类型校验和规则，语义歧义通过上下文核对或必要澄清处理，并纳入真实场景回归。

内容完整性按项验收：用户要求三个子事项就核对三个目标都存在，指定的微信、路径、说明保真，不能以结构合法代替内容正确。仅要求一个任务改期，不等于授权改变项目硬截止、其他事项或固定日程；预计展示跨度等派生信息与用户明确承诺分开处理，超出本次范围的必要联动在原处说明。

除同operationId防技术重试外，还要处理用户换句话重复交代：结合近期执行回执、目标对象和明确指代判断是否已经完成；确实是原事项就引用或修改原ID，疑似重复时原地澄清，不能仅凭同名合并。“再建一份”“下周再安排一次”等明确新增不应被去重吞掉。

保存完成后，用同一operationId查询持久回执，核对记录ID、实际变更字段及关联；界面更新使用确认的服务端结果。若此时其他设备又修改了记录，应区分本次操作结果与后续变化，不能把后续版本当作本次失败而再次覆盖。

| 执行状态 | 对用户的反馈 | 系统处理 |
|---|---|---|
| 已确认保存且结果符合请求 | “已把摄影课小林的微信改为…；其他项目角色保留。”附原地查看/撤销 | 完成该执行项，更新界面和相关事实 |
| 保存响应丢失，尚未核实 | “正在核对是否已经保存，输入还在。” | 用原操作ID查回执，禁止生成新ID盲目重做 |
| 必需字段、对象或选择未明确 | 精确指出一个阻碍执行的问题；其他独立已完成项照实显示 | 保留完整上下文，只暂停依赖该答案的操作组 |
| 发现版本冲突或结果异常 | 显示具体冲突/不一致，不声称已完成 | 记录诊断，保留原请求；只有仍符合用户原意且前置版本有效的动作可安全重试 |

提供按本次变更撤销的入口，撤销前检查受影响字段是否已被后续操作改变；不能用整份旧快照覆盖新工作。历史保留操作来源与前后值，支持解释“为什么这里变了”。

能力边界按工具实际效果表达：“更新工程路径记录”与“把另一台电脑的文件搬过去”是两件操作；“记下要联系谁”与“发出微信”也是两件操作。没有实际设备/外部应用工具或结果时，不能把更新记录说成已经完成外部动作。

新增验收：对新增、字段修改、追加、替换、改期、取消、重开分别测试对象准确、内容完整、关系正确、只执行一次、未越过修改范围以及保存后可见；手打和语音使用同一组验收。明确执行指令必须真正落库；只读或“先看看”必须保持业务零写入。

## 5. 能够日常使用的验收门槛

### 自动校验与故障测试

1. 失败原话可恢复；旧草案失效后不能再应用；同一操作重试只产生一次业务结果。明确执行指令正确落库，只看建议时零业务写入。
2. 负向意图涉及的对象不在最终执行集合；正文、方案、保存结果逐项一致。
3. 未确认推断不能成为已存业务事实；同一事实当前只有一个有效版本，明确的不同日期例外另存。
4. 固定时段、路程、硬截止及明确结束时间不被静默违反；不可行必须解释。
5. 模拟收到回执前断网、服务端已成功而前端超时、刷新、双标签编辑同一字段，以及旧请求晚到。不能丢内容、重复执行或旧结果覆盖新改口。
6. 执行后项目/任务/联系人/跟进/文件关联有效；重开任务、完成部分依赖、只收到部分资料均保留正确状态。新增不漏项，修改只影响指定字段，追加不覆盖，回执与实际结果一致。

### 真实使用验证

- 两份报告中的39轮对话及浏览器故障场景作为诊断和回归素材。日期规则测试使用固定时钟；新一轮真实Qwen测试按当日日期重建场景。业务规则用确定性测试验收；模型理解再跑改写后的连续场景，不能只背过原来的句子。
- 用同一隔离工作空间跨日继续：至少覆盖三天与多次重新打开，回查第一天的工程、微信和承诺；改期后再问时不能读取旧版本。
- 在真实网页上以两个入口走完接项目、安排、催办、收件、部分完成、返工和晚间收尾。路径复制、手机点按详情、键盘焦点、窄屏输入及滚动都实测。
- 语音使用真实转写和播放链路，覆盖同音人名、日期改口、停顿、打断、权限拒绝和转写中断；没有实测麦克风的场次不得写成麦克风验收通过。
- 负载使用明确数据集分层测试，例如20个活跃项目、500件事项、2000段日程及持续历史，验证搜索/同步/首屏与上下文选取；这些是待验收基线，不是当前容量承诺。接近硬上限时应有归档与导出方式，不能以截断历史假装解决长期增长。
- 输入应立即显示接收/未同步状态；模型处理显示可恢复进度，不锁住继续记录。记录首反馈及完成耗时分布，以实际服务数据制定目标，不把接口200当作使用成功。

发布前门槛：丢输入、错误执行、静默时间违约、取消失效、活跃矛盾事实、跨账户数据混用均为阻断项；核心读/改/撤回/分析/推荐流程必须满足上述验收。仍存在阻断项时，保留已验证的原文记录与手工操作能力，并明确自动安排尚未完成验证。

## 6. 一段应该成立的使用体验

用户：“先帮我看看怎么排：明天去银行十一点半前办完，办事半小时，路上二十分钟。大纲一小时别动，填表挪下午一点。哦小林例图先别催。”

助手先核实大纲是否真的已有时段。若此前未排成功，直接说明“那一小时还没保存”，不假装保留了不存在的安排。其他已明确部分继续给出：10:40出发、11:00–11:30银行、13:00–13:40填表，以及取消课程小林催办。若路程与固定安排冲突，说明冲突并给选择。

用户：“银行不去了，线上办好了，其他照旧。”

同一张变更卡移除银行及关联路程，保留填表和不催小林的决定，旧卡失效。用户说“就按这版”或点击确认后，Agent实际保存并核对结果，给出精确回执。下一天问“安排了什么”，银行不会从旧记忆里重新出现。整个过程都在当前入口完成。

另一个明确指令：“把快闪工程记录更新为家里电脑的 E:\工作\快闪秋季，在说明后面补一句‘印刷稿还没定’，其他不动。”对象和路径明确时直接更新原工程记录、追加说明并核对；回复实际变化。原说明、项目关联和联系人不能被覆盖，也不能声称已在电脑上移动文件。
